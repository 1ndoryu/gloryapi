## 11826-1 — Hook universal de confirmación de cierre en el bridge de Codex Desktop

**Qué se hizo** (sustituye la heurística de `10826-1`; el diagnóstico del thread
`019fee99` mostró que "Sigo la auditoría leyendo..." —gerundio de continuación— no
matcheaba la regex y el falso complete volvía a escaparse):

El usuario pidió que, en vez de adivinar con una heurística, el bridge **pregunte al
modelo** si realmente terminó. El hook es universal: toda respuesta final sin
`tool_calls` (con tools del usuario disponibles y sin haber ejecutado ninguna tool en
el turno) recibe UN request de confirmación con `CONFIRM_DIRECTIVE`: si realmente
terminó, que responda únicamente "ok"; si le queda algo, que continúe en el mismo
turno invocando la herramienta. "ok" confirma el cierre **sin re-activar el hook**;
cualquier otro texto se descarta y se cierra con la respuesta original.

- **`CONFIRM_DIRECTIVE`** (reemplaza `NUDGE_DIRECTIVE`): texto de confirmación de
  cierre ("si realmente has terminado... responde únicamente 'ok'... si no,
  continúa AHORA...").
- **`isConfirmationText(text)`**: detecta la confirmación concreta (ok/okay/okey/kk/
  done/yes/sí/listo/hecho/terminado/completado/finished/all done/eso es todo/ya
  está/nada más/perfecto/vale/de acuerdo/entendido/confirmado + variantes "ok
  done/listo/hecho/..."). Normaliza puntuación a espacios y **rechaza "ok, pero
  falta X"** (no es cierre real).
- **Gatillo universal** (streaming y non-streaming): `tool_calls` vacíos + texto +
  `chat.__userTools === true` (tools del usuario, no las inyectadas
  `node_repl`/`automation_update`) + tools presentes + **sin `tool` messages en el
  turno** (si ya ejecutó, el cierre es legítimo y no se pregunta) + `NUDGE_RETRIES>0`.
- **`__userTools`**: flag no-enumerable en `translateRequest` (no se serializa a
  upstream). En `runInternalWebToolLoop` el spread no copia no-enumerables → se
  re-define en `working`; el non-streaming usa `gateChat = resolved.working` para el
  gatillo (si no, el web loop non-streaming disparaba un request extra).
- **Ramas de log**: `nudge_retry` (el retry trae tool_calls → se emiten como
  function_call), `nudge_confirm` ("ok" → cierre real con el texto original),
  `nudge_noop` (otro texto → se descarta). `intent` con `isFutureIntentNarration`
  queda solo como telemetría (ya NO gatilla).
- **Coste**: +1 request por respuesta final legítima con tools del usuario y sin
  haber ejecutado tools. El "ok" nunca aparece como texto visible para el usuario.

**Archivos**:
- `integrations/codex-bridge/bridge/server.js` (CONFIRM_DIRECTIVE, isConfirmationText,
  buildNudgeChat/nudgeForToolCalls con `text`, gatillos universales con `__userTools`
  y guard de turno sin tools, `gateChat` en web loop non-streaming, logs
  `nudge_confirm` + `intent`).

## 11826-2 — Timeout upstream a 6 min + recuperación por timeout en el bridge

**Qué se hizo** (diagnóstico de las sesiones `019fee99` / `019fee93` con
"stream disconnected before completion: upstream timed out after 180000 ms"):

El mensaje lo forma el CLIENTE Codex Desktop cuando el bridge corta el SSE con
`response.failed`. El timeout de 180 s es **por request individual** del bridge
(`fetchUpstreamCompletion`), no por turno. Los 2 `web_loop_error` (502) de las
05:42Z correspondían a requests del **web loop interno** iniciados a las 05:39:31/45
que cayeron a los 180 s exactos con contexto enorme (~117k tokens de input,
`cached_input_tokens: 0`). Las sesiones NO se atoraron: `019fee93` cerró con
`task_complete` útil a las 05:47:03Z y `019fee99` siguió trabajando (05:48-05:50Z).
El web loop NO tenía recuperación: el error se propagaba directo a `response.failed`.

Cambios en `integrations/codex-bridge/bridge/server.js`:
- **`UPSTREAM_TIMEOUT_MS`** default **180000 → 360000** (6 min), rango máx.
  **300000 → 600000** (10 min vía `BRIDGE_UPSTREAM_TIMEOUT_MS`).
- **`UPSTREAM_TIMEOUT_RECOVERY_MS`** (nueva, default **720000** = 2× base, rango
  1000-1200000 vía `BRIDGE_UPSTREAM_TIMEOUT_RECOVERY_MS`): ventana del reintento.
- **`fetchUpstreamCompletion`**: marca `error.__timedOut = true` cuando aborta por
  timeout (distingue timeout real de otros fallos upstream).
- **`fetchWithTimeoutRecovery(chat, authorization)`** (nueva): si el primer intento
  aborta por timeout, reintenta **UNA vez** con la ventana extendida y registra
  `kind: 'upstream_timeout_retry'`. Cualquier otro fallo se propaga igual.
- Usada en el **web loop** (`runInternalWebToolLoop`) y en el **non-streaming**
  non-web (`nonStreamingChatToResponses`). El streaming directo no aplica: su abort
  depende del cliente (no tiene timeout propio del bridge).

**Archivos**:
- `integrations/codex-bridge/bridge/server.js` (constantes, `__timedOut`,
  `fetchWithTimeoutRecovery`, web loop y non-streaming).
- `integrations/codex-bridge/test/mock-http-contract.test.cjs` (env
  `BRIDGE_UPSTREAM_TIMEOUT_RECOVERY_MS: '500'`; assert de mensaje genérico
  `/\d+ ms/`; nuevo assert: 2 bodies colgados = el timeout reintenta una vez).

**Evidencia / tests**:

- `anti-falso-complete.test.cjs`: **8/8 PASS** (sin regresión del hook).
- `mock-http-contract.test.cjs`: **PASS** (3578 ms; verifica recuperación: 2 bodies

- Bridge reiniciado: PID 31932, `http://127.0.0.1:4100/health` OK.
- Commit: pendiente (rama `gloryapi`). Sin push (requiere autorización explícita).

**Decisiones / gotchas**:
- Un solo reintento: si la ventana extendida también hace timeout, se propaga el

- El reintento es seguro en el web loop: el round no muta `working` hasta después
